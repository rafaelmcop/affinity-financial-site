# WhatsApp service modes

Admin → Users → Edit → Functions and permissions controls the account mode. Existing enabled grants migrate to Full without requiring a new QR. New users remain disabled until an authorized Admin grants Send only or Full. Assigned assistants have an independent mode for their own WhatsApp, editable by the Admin in their user editor. Mode changes are audited. The physical connection remains one browser per account; the runtime ceiling remains five. Reduced disk and portal synchronization work is expected, but five-account memory savings have not been measured and browser transport still receives the WhatsApp protocol.

Send only retains QR pairing, portal sends and delivery status. Incoming message handlers return before downloading media or writing history. Portal-created outgoing messages and attachments remain available for communication audit and the existing retention rules. Attachment reads require a sent record owned by that account. Chat/message directory reads, deletion and restoration are rejected server-side. Full retains existing messenger behavior. Disabling stops the browser without logging the phone out; re-enabling can restore valid saved authorization.

Both modes automatically import available contacts, including every group, after each actual browser connection. A server-side job checks ready sessions every minute, keys work by owner and connection ID, resumes in batches and deduplicates via the existing central-lead/source tables. The importer preserves own-agent visibility, Admin visibility, source attribution, international separation and group exclusions. It does not require the messenger page to stay open. Completed imports release the in-memory group/contact snapshot and mark the existing setup job complete. Existing collection information in the connection interface remains visible; no additional pop-up interrupts the user.

Mode and monotonic revision are carried inside the signed bridge ticket and persisted locally. Stale or legacy tickets cannot upgrade a previously restricted account. A failed policy push remains pending and retries through scheduled maintenance. The Worker denies reads immediately according to its current grant. The bridge continues enforcing automatic-send daily quotas, expiry and spacing.

Tests use a fake WhatsApp provider with a temporary database and no network message transport. They verify pairing, group collection, outgoing audit, media isolation, received-message suppression, stale-ticket rejection, independent account policies and both messenger layers above toolbar controls at small viewports. Real accounts are not used for test sends.
